### 7. Technical Highlights (60 seconds)

**Say**:  
"Let me briefly explain the core algorithm:

**Hall Selection**: We always try the preferred venue first, selecting the smallest hall that fits the attendees. If no suitable hall is available, we fall back to other venues in deterministic order.

**Resource Tracking**: We use a sweep-line algorithm to calculate concurrent resource usage. Instead of just counting overlapping bookings, we track the exact quantity of each resource in use at every moment during the event's reserved interval.

**Conflict Detection**: We use half-open interval overlap checking—the industry standard. Events that touch exactly at a boundary don't conflict, but setup and cleanup buffers typically create overlaps even for back-to-back events.

**Data Persistence**: All bookings are stored in an SQLite database with indexes on date, venue, and status for fast queries. The system maintains full history including rejected bookings for audit purposes."

## ❓ Anticipated Judge Questions & Answers

### Q1: "How do you handle concurrent requests from multiple users?"

**Answer**:  
"We use SQLite with WAL (Write-Ahead Logging) mode and the better-sqlite3 library, which provides synchronous operations. This prevents race conditions where two requests might try to book the same resource simultaneously. For production scale, we'd upgrade to PostgreSQL with explicit transaction locks and optimistic concurrency control using version numbers."

---

### Q2: "What happens if someone tries to book an event that spans multiple days?"

**Answer**:  
"Currently, the system is designed for single-day events as per the hackathon requirements. The validation layer enforces that event_date is a single date, and times are within that day. For multi-day events, we'd extend the schema to have event_start_date and event_end_date, then modify the conflict detection to check for overlaps across date ranges."

---

### Q3: "How do you ensure data consistency when rescheduling fails?"

**Answer**:  
"Rescheduling is implemented as an atomic operation. When a reschedule request comes in, we:
1. Validate the new request parameters
2. Run the allocation algorithm with `exclude_booking_id` set to the current booking ID, so it doesn't conflict with itself
3. Only if allocation succeeds, we UPDATE the booking record

If any step fails, we return an error, and the original booking remains completely unchanged in the database. No partial updates occur."

---

### Q4: "Why use the sweep-line algorithm for resource checking instead of simpler counting?"

**Answer**:  
"Because different bookings request different quantities of resources. For example:
- Booking A might need 2 projectors
- Booking B might need 1 projector
- Both during 10-11 AM

If we just counted overlapping bookings, we'd see 2 bookings and couldn't tell if we have enough projectors. The sweep-line algorithm tracks the exact concurrent usage at every time point. We create 'start' and 'end' events for each booking's reserved interval, sort them by time, and sweep through maintaining running totals. The moment usage exceeds capacity, we reject the request."

---

### Q5: "How did you decide on the smallest-hall-first strategy?"

**Answer**:  
"This is a resource optimization strategy. By allocating the smallest suitable hall, we:
1. Leave larger halls available for events with more attendees
2. Minimize wasted capacity (50 people in a 250-seat hall is inefficient)
3. Maximize the probability of accommodating future requests

This is similar to the 'best-fit' algorithm in memory allocation. The problem statement explicitly requires this behavior."

---

### Q6: "What if two halls have the same capacity?"

**Answer**:  
"We use deterministic tie-breaking: among halls with equal capacity, we select the one with the lowest ID. This ensures reproducible behavior—the same request always gets the same result. In a production system, we might also consider factors like hall features, recent usage patterns, or proximity to parking."

---

### Q7: "Can a client book multiple events at the same time?"

**Answer**:  
"Yes, the system allows it. There's no constraint preventing a single client from having overlapping bookings—they might be running concurrent sessions at different venues. The resource constraints apply at the venue level, not the client level. However, we could add a business rule to flag or prevent this if needed."

---

### Q8: "How do you handle time zones?"

**Answer**:  
"Currently, all times are treated as local time at the venue location. We use date-fns for time manipulation which handles string-based time comparisons consistently. For a global deployment, we'd:
1. Store all times in UTC in the database
2. Convert to venue's local timezone for display and validation
3. Add a timezone field to the venues table"

---

### Q9: "What happens if the database file gets corrupted?"

**Answer**:  
"SQLite with WAL mode is very resilient to corruption. For production, we'd implement:
1. Regular automated backups
2. Point-in-time recovery
3. Database replication
4. Integrity checks on startup

For the hackathon, the database is recreated easily by running the seed script."

---

### Q10: "How would you scale this to hundreds of venues?"

**Answer**:  
"The current O(V × H × B log B) complexity would need optimization:

1. **Database indexes**: Already implemented on (venue_id, event_date, status)
2. **Caching**: Cache venue configurations in memory (they rarely change)
3. **Parallel search**: Search multiple venues concurrently using worker threads
4. **Pre-filtering**: Eliminate venues that can't possibly satisfy the request (capacity too small, insufficient resources) before checking availability
5. **Partitioning**: Partition bookings by date ranges for faster queries

For 100 venues with 200 halls and 10,000 bookings/day, we'd likely migrate to PostgreSQL with connection pooling and implement a read-replica strategy."

---

### Q11: "Why did you choose SQLite over PostgreSQL or MongoDB?"

**Answer**:  
"For the hackathon scope, SQLite offers:
- ✅ Zero configuration—no separate database server
- ✅ ACID compliance for data integrity
- ✅ Fast synchronous operations
- ✅ Single-file portability
- ✅ Excellent for read-heavy workloads

SQLite handles thousands of bookings easily. For production with concurrent writes and multiple app instances, we'd upgrade to PostgreSQL while keeping the same relational schema."

---

### Q12: "How do you prevent SQL injection?"

**Answer**:  
"We use parameterized queries exclusively via better-sqlite3's prepared statements:

```javascript
db.prepare('SELECT * FROM bookings WHERE id = ?').get(bookingId)
```

The `?` placeholder ensures user input is properly escaped. We never concatenate user input into SQL strings."
